## モデルのランキング（3軸）

| モデル | コスト | 知性 | 趣味の良さ |
|---|---|---|---|
| GPT-5.5（Codex 経由） | 9 | 8 | 5 |
| Sonnet 5 | 5 | 5 | 7 |
| Opus 4.8 | 4 | 7 | 8 |
| Fable 5 | 2 | 9 | 9 |

- **コスト**：数値が高いほど安い（実質無料〜高コストの順で 9→2）
- **知性**：無監督でどれだけ難しい問題を任せられるか
- **趣味の良さ**：UI/UX・コード品質・API設計・文言の質

> **⚠️ 5co 適用時の注意（コスト列は転用不可）**：この表のコスト列は Rootport 氏個人の
> 実支払い（「OpenAI の利用上限が寛大なので GPT-5.5 は実質無料」）に基づく値であり、
> 5co の契約条件をそのまま反映したものではない。したがって**「バルク作業＝GPT-5.5」の柱は
> 5co では弱く、バルク・機械的作業の既定は Sonnet に寄せる**。GPT-5.5 は
> `scripts/codex-call.sh` が安定稼働している範囲で「レビュー時の独立した別視点」として
> 併用するに留める（Codex CLI ラッパー経由でしか呼べず、運用上の失敗面が増えるため）。
> 5co の実コストを棚卸しして表を作り直すまでは、コスト列は参考値として扱うこと。

## 適用ルール

1. **これらは既定値であってハードリミットではない**
   安いモデルの出力が基準に達しない場合、確認を取らずに上位モデルで再実行してよい
   （= 標準的な許可がある）。出力の質で判断し、価格タグでは判断しない。
   ミディオカな成果物を出すより、コストを上げる方が安く済む。
2. **軸が衝突した場合のタイブレーク順**：成果物として出すものは
   **知性 > 趣味の良さ > コスト**
3. **バルク・機械的作業**（仕様が明確な実装・データ分析・移行作業）→ 原文では **GPT-5.5**
   （実質無料）だが、上記の注意のとおり **5co では既定を Sonnet とする**
4. **ユーザー向けの成果物**（UI・文言・API設計）→ 趣味の良さ ≥ 7 のモデル
   （Opus 4.8 / Fable 5 / Sonnet 5）
5. **プラン・実装のレビュー** → **Fable 5 または Opus 4.8**。追加の独立視点が欲しければ
   GPT-5.5 を第三の視点として併用してよい
6. **Haiku は使わない**
7. **本体（司令塔）は監督役に徹する**：実装・テスト・調査そのものを本体が抱え込まず、
   Agent tool で専門サブエージェントに委譲し、本体はタスク分解・レビュー・統合に専念する
8. **小タスクは委譲しない（損益分岐）**：委譲には手渡しごとにほぼ固定の調整コストがかかる
   （指示書・報告書の境界トークンは双方で二重課金＋ワーカー間の重複調査）。ワーカーが吸収する
   トークン量がこれを上回る大きな作業だけ委譲し、小さな作業は本体がそのままやる。
   ルール7はこの条件付きで適用する（実測は「タスク形状と委譲の損益分岐」節）
9. **探索的タスクはアドバイザー・チェックポイント型**：実験・調査・デバッグなど結果を見て
   方針が変わるタスクは、判断を前倒し（詳細な事前計画）せず、安い実行役＋高いモデルへの
   定点相談（例：20実験中2回）で舵取りする。安いモデルは限界利得の山登りにハマって
   後戻りしない癖があり、定点での再優先順位付けがそれを補正する
10. **ワーカーは使い回してキャッシュを蓄積**：サブエージェントを呼び出しごとに新規スポーンせず、
    同一ワーカーへの継続送信（SendMessage / 会話継続）でプロンプトキャッシュを効かせる。
    キャッシュヒット率が低いと、安い単価のモデルを使う利点がコンテキスト再書き込み費で消える
11. **ワーカー失敗は隔離し、有界で再起動する（異常系の既定）**：委譲したサブエージェントの
    死・タイムアウト・throw は、オーケストレーション層で1体に隔離し全体を巻き込まない
    （`agent()` の `null` 返却＋`.filter(Boolean)`／`parallel`・`pipeline` の項目単位 null 化）。
    再起動は「文脈を捨てて新規スポーン」か「`SendMessage` で文脈を保って継続」を、コンテキストの
    資産価値で選ぶ。リトライは無限にせず**有界回数＋停止条件**を必ず置く。ルール7〜10 が正常系
    （いつ委譲するか）なのに対し、本ルールは異常系（落ちたらどうするか）を定める
    （詳細＝「ワーカー失敗の隔離と再起動」節）

## タスク形状と委譲の損益分岐（Lance Martin 実測・2026-07-10）

ルール 8〜10 の根拠となる2実験の要点。

- **Parameter Golf（ML 実験自動化・探索的タスク）**: Sonnet 5 実行役＋Fable 5 への定点相談
  （初期計画＋20実験中2回のチェックポイント）で、**Fable 単独の改善幅の約90%をコスト約34%で達成**。
  ただし効いたのはチェックポイント相談のみで、**事前計画の助言はほぼ無価値**
  （Fable の初期ランキングは実結果と逆相関）。探索的タスクでは判断は前倒しせず散りばめる。
- **BrowseComp（Web 調査・規模で損益が反転）**: 小規模（1問 約0.37M トークン）では
  オーケストレーション構成が **+60% のコスト増で性能向上ゼロ**＝Fable 単独の方が安い。
  大規模（1問 約31M トークン）では委譲が回収でき、**スコア96%をコスト46%で達成**。
- **含意**: 「監督役に徹して委譲」（ルール7）は万能ではなく、委譲で安くなるのは
  調整コスト（境界の二重課金・ワーカー重複）を吸収トークン量が上回る場合だけ。
  Fable 5 は安いモデルよりトークン効率が良いことがあり、単価差だけで委譲を正当化しない。

## ワーカー失敗の隔離と再起動（異常系の設計・Graph engineering 由来）

ルール 11 の詳細。出典4の Graph engineering 層＝*node failure isolation / state consistency /
recovery paths* を、本リポの Agent/Workflow ツールの実メカニズムに接地したもの。
ルール7〜10 が「いつ・どのモデルに委譲するか」（正常系の損益分岐）を扱うのに対し、
本節は「委譲したワーカーが落ちたらどう続けるか」（異常系）を扱う。3つの機構で構成する。

### 1. 隔離（node failure isolation）— 1体の死を全体に伝播させない

- `agent()` はリトライ後の致命的 API エラーで**例外を投げず `null` を返す**。受け側は
  `.filter(Boolean)` で死んだワーカーを除いて続行する
- `parallel(thunks)` は thunk が throw しても呼び出し自体は reject せず、その要素だけ `null` に
  なる（バリアは全体を巻き込まない）
- `pipeline` はある stage が throw するとその item だけ以降の stage をスキップして `null` に落ち、
  他 item は進む
- → **「N体のうち1体が落ちても残り N−1 の成果は回収する」を既定**にする。1体の失敗で全滅する
  all-or-nothing 構成にしない

### 2. 状態一貫性（state consistency）— 並列書き込みの衝突を防ぐ

- ファイルを**並列で書き換える**ワーカーは `isolation: "worktree"` で各自の git worktree に
  隔離する（未変更なら自動破棄）。読み取り専用の並列にはコスト（~200-500ms＋ディスク）に
  見合わないので付けない
- 共有状態は「全ワーカー完了後に本体が1回マージ」（バリア）で確定し、ワーカー同士で直接
  触らせない

### 3. 再起動・復旧経路（recovery paths）— 落ちた後の続け方を2択で持つ

- **新規スポーン**（`Agent` 再呼び出し）：文脈を捨ててやり直す。状態がプロンプトに全部載る
  小タスク向き
- **文脈保持の継続**（`SendMessage` で既存ワーカーに追送信）：積み上げた調査・キャッシュを
  捨てずに再開する。コンテキストが資産の探索タスク向き（ルール10 のキャッシュ蓄積と同じ理由）
- **停止条件は必ず有界**：リトライは無限ループ禁止（出典4 の Loop engineering「証拠ベースの
  停止条件」）。有界回数＋loop-until-dry（K回連続で新規ゼロなら打ち切り）で収束させる。
  CLAUDE.md の「同じ不具合を2回直して解消しなければ Codex に委譲」は、この停止条件の一形態

### 運用の既定：落ちうる前提で書く

委譲コードは「happy path だけ書いて例外を握り潰す」のではなく、`.filter(Boolean)` で欠損を
明示的に扱い、`log()` で**どのワーカーが落ちて何体で続行したか**を可視化する。silent な件数減は
「全部やった」と誤読される（＝ CLAUDE.md「回答前の自己検証」2. 実証ベースの完了報告と同じ罠）。

## Claude Code 上での実装方法

Claude Code の Agent tool は呼び出し時に `model` パラメータ（`sonnet` / `opus` / `haiku` / `fable`）
を受け取れる。サブエージェント定義（`.claude/agents/*.md` の frontmatter）でも `model` を固定できる。

- **Claude モデル**（Sonnet 5 / Opus 4.8 / Fable 5）は Agent/Workflow の `model` パラメータで直接指定する
- **GPT-5.5** は `model` パラメータでは指定できない（Claude モデルのみ受け付ける）ため、
  ラッパー経由で呼ぶ：
  - `model: "sonnet", effort: "low"` の薄い Claude ラッパーサブエージェントを立て、
    そのプロンプトで「自己完結した codex プロンプトを組み立てて `codex exec` を Bash 経由で
    実行し、結果をそのまま返す」よう指示する
  - このリポジトリには既に `scripts/codex-call.sh`（GPT-5 呼び出しラッパー、`docs/multi-llm-orchestration.md`
    の「参謀」役）があるため、直接呼び出しにはそちらを使ってよい
- 省略時はセッションのモデルを継承する点に注意（Fable 5 セッション中に `model` を明示しないと
  そのまま Fable 5 が引き継がれる）
- この運用ルール自体は自然言語の指示（本ファイル・CLAUDE.md）で足りる。Claude Code 自身が
  `.claude/agents/*.md` や `model` パラメータを解釈して従うため、個別の設定ファイルを
  都度手書きする必要は基本的にない

## CLAUDE.md 既存方針との関係

CLAUDE.md の「コスト管理」節（デフォルト Sonnet・高度推論のみ Fable/Opus に切替）と矛盾しない。
本ルールはそれをサブエージェント委譲の文脈で具体化したもの：
「機械的な生成・検査・定型作業＝安いモデル／文言の質・数値の自己検証・戦略判断＝高いモデル」
という軸を、コスト・知性・趣味の良さの3軸評価表として明文化し、
**「基準に届かなければ黙って upgrade してよい」という標準許可**を追加した。

## 展開経路（このルールがどこに届くか）

1. **git 派生リポ**：`apply-template.sh` の ROOT_FILES に本ファイルを登録済み。加えて
   `.claude/scripts/session-context.sh` の⑦ブロックが「適用ルール」節を SessionStart で自動注入する。
   `sync-template` → `merge-template-sync-prs` で全派生リポへ伝播する。
2. **非 git の Drive 作業場（`AI-Objective-MGMT` 等・GitHub 不要の社員向け）**：本ファイルや
   `session-context.sh` は Drive フォルダに配布されない。代わりに `scripts/drive-canonical-refresh.sh`
   が Drive 直下 `CLAUDE.md` の「CI 正本ブロック（マーカー方式）」内・**コスト管理（全セッション必須）節**へ
   本ルールの要点を**インライン**で焼き込む（毎日 08:00 の cron／手動実行の両方で更新）。Drive フォルダには
   `docs/…` 参照が存在しないため、リンクではなくルール本体を書き込む設計。これにより「Drive 直下で作業する
   全社員のセッション」にも、毎ターン注入される CLAUDE.md 経由でルールが届く。
   - 管理者 Mac で即時反映する場合：`DRY_RUN=1 bash scripts/drive-canonical-refresh.sh` で計画確認 →
     `bash scripts/drive-canonical-refresh.sh` で本番。`AI-Objective-MGMT` 以外のマウント（例：
     `自社OKR会/KR-1A`）は自動検出対象外のため、必要なら `DRIVE_ROOT=<パス> bash scripts/drive-canonical-refresh.sh`
     で個別指定する（CI-kit を持たない作業場では CI-kit 同期分が新規作成される点に留意）。

## 適用範囲外（例外）

- ユーザーが明示的にモデルを指定した場合はそれに従う（本ルールはデフォルト方針）
- 本体（司令塔）自身のモデル選択は対象外。CLAUDE.md の既存コスト管理方針に従う
