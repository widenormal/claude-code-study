## 1. 起きたこと（事実）

KR-S1 推計の「行がない月」の原因調べ（2026-11-27 4時台）で、次が起きた。2026-11-26 にも同じ指摘（#1427）があった。

1. 回し方：T3 は通した。ただ、1つの作業を1つのモデル（Claude と Codex が別々に）が書くだけで、別のハイエンドモデルによる照合がなかった。Gemini も使っていない。T3 も `( … &)` で切り離して起動した（切り離しは `rules/2026-11-16_no-silent-stall.md` で禁止）。
2. 起動先と `projects/` は守れた。
3. 起動前に台帳を読んだか、自分の行を足したかが確かめられない。

## 2. 原因（須藤 航@tw1 の見立て）

- 指示文のたびに決まりを記憶から書き写すので、照合や台帳が抜ける。
- 実際に動くのはバックグラウンドの作業者で、決まりを毎回読み直さない。
- #1427 でチェックは全Bot必須になったが、機械で止める仕組みがない。

## 3. 「別のハイエンドモデルで照合」は正本でどう決まっているか（調べた事実だけ）

| 見つかったもの | 出どころ | 範囲 |
|---|---|---|
| システム開発は、完了報告の前に別系統の Codex で検品する（fresh context の別モデル）。PR では `.github/workflows/codex-inspection.yml` が自動で動く | `.claude/skills/codex-review.md`「完成時検品（システム開発の完了ゲート）」、template の CLAUDE.md「Codex 4原則」3 | **システム開発だけ**。照合モデルは Codex（`scripts/llm-models.conf` の `CODEX_FRONTIER_MODEL`） |
| 重要な設計・戦略・リスク判断では Codex の独立意見を取る | template の CLAUDE.md「Codex 4原則」1 | 判断の相談。照合（検品）の必須化ではない |
| 開発委譲の例外：原則は Claude が実装し Codex が独立検品する。完了条件と変更境界が決定論的な例外タスクでは、Codex は read-only でパッチ提案まで行い、適用・テストと別系統による検品は Codex 以外が担う。Codex に「修正案作成」と「最終検品」を同じ文脈で行わせない | `.claude/skills/codex-review.md`「開発委譲の例外規定」 | 開発委譲（システム開発の例外） |
| Gemini は「実装の別視点・コードの違うバイアス」に使う | `.claude/skills/codex-review.md`「使い分け（vs Gemini）」 | 使い分けの目安。必須ではない |
| 二段（通常使用／高度な検証）のモデル割当。長文・設計・レビューの「高度な検証」は `claude-opus-5-5` で点検 など | `rules/2026-11-24_t3-harness-relay.md` §4.4 | **案**。§10-15・16 は未決 |
| 長文の照合の回し先は Gemini 4 Carbon | `rules/2026-11-15_grok-minimal-multillm.md` 回し先表 | 回し先の目安。照合を必須にする決まりではない |

**結論：** 既存の決まりは次の2つに分けて読む。
- **原則（システム開発）：** 完了報告の前に別系統の Codex が検品する。
- **既存の例外（開発委譲）：** Codex がパッチを提案した作業では、適用・テストと別系統の検品は Codex 以外が担う（検品者は Codex に固定されない）。
- Gemini を必須にする決まりは、どちらにも**無い**。

この既存の規定の外へ必須範囲を広げる部分（文書・ルール・調べものなど、システム開発以外の取り次ぎ）は、§5-1 で決まった（本文の作業はすべて書き手と別のモデルが照合。Gemini は必須にしない）。

この文書では、正本に無い呼び名は使わない（`rules/2026-11-22_no-invented-terms.md`）。

## 4. 仕組み

### 4-1. 取り次ぎ指示文のひな形

- `docs/agents/templates/handoff-task.template.md`
- 置き場所の理由：`docs/agents/` は全Botが読む `/workspace/knowledge/agents/` の写しで、正本の `rules/` と並べると探しやすい。ひな形は正本（決まり）ではないので `rules/` とは分けた。
- 毎回書き写していた決まりを、ひな形の中に**本文として固定**した（「〔固定〕」を含む行）：3層のパス欄、合格条件欄、やらないこと欄、用語を作らない1文、progress.md の書き方、LLM行、台帳（読んだ・足した・消す）、照合の欄（本文の作業はすべて書き手と別のモデルが照合する。照合モデルと記録先は空・「なし」不可。Gemini は任意）、切り離し禁止の1文、提出前チェック。

### 4-2. 作業者への前置き

- `docs/agents/templates/worker-preamble.md`
- 「作業の前に、次の正本を読み直してから動く（記憶で書き写さない）」と、正本の GitHub URL 一覧。
- 入口スクリプトが指示文の**先頭に自動で付ける**。指示文に書き写さない（写しが古くなるのを防ぐ）。

### 4-3. 入口スクリプト `scripts/handoff-launch.sh`

0. `--task`・`--progress`・`--preamble`・`--template`・`--launch-dir` は最初に絶対パスへ直す（呼び出した場所を基準）。起動場所へ移っても同じファイルを読み書きする。
1. task ファイルが、ひな形の見出し（`## `）と固定行を全部含むかを、行ごとに完全一致で確かめる。ひな形の説明コメント（`<!-- … -->`、消してよい）の中は見ない。`--template` を渡しても標準のひな形の行は必ず確かめる。
   - 必須の欄（層1〜3のパス・起動場所・`output_dir`・progress.md のパス・台帳を読んだ・自分の行の場所と session_id・照合モデル・記録先）は、ひな形とは別にスクリプトの中の一覧で、欄があるか・値が空でないかを確かめる（ひな形を差し替えても外せない）。
   - 照合モデル・記録先は「なし（理由：…）」も認めない（§5-1）。照合モデルが書き手（`--model`）と同じなら起動しない。
   - 二重の波かっこの欄が残っていても起動しない。
2. `scripts/pillars-preflight.sh` を呼ぶ（台帳の自分の行・task と指定ファイルの切り離し検出を含む）。不合格なら起動しない。
3. `test -f <起動場所>/AGENTS.md`。
4. 合格したときだけ `t3 thread start . --provider … --model … --option … --wait -` を**前面で**実行する。標準入力は「前置き＋task」。切り離しは使わない。待つ側は、このスクリプトを Shell ツールのバックグラウンド起動（`block_until_ms 0`）で呼ぶ。
5. 前置きと task を起動前に読み切る（読めなければ起動しない）。起動の行を progress.md に1行追記する（書けなければ起動しない。LLM行は T3 側が書く）。t3 が失敗で終わったら `BLOCKED` を1行。
- 値を取るオプションに値が無ければ使い方を出して終わる（3本とも）。
- `timeout` コマンドに頼らない（Rutzbo〈macOS〉には `timeout` が無い。§9）。
- macOS 標準の `/bin/bash`（3.2）で動く書き方にしている（テストも `/bin/bash` で通す）。
- `--dry-run`：起動せず、確かめた結果と起動するコマンドを表示する。
- スクリプト自身に、切り離しの語とアンパサンドの文字を1つも入れていない（テストで確かめる）。

### 4-4. preflight／postflight の追加（読み取りだけ・ファイルを消さない）

| 追加 | preflight | postflight |
|---|---|---|
| 台帳の自分の行（`--session-id`） | 台帳フォルダ → 同じ git の「ledger」を名前に含む枝 → 未マージの台帳 PR（gh。無い・未ログインなら警告だけ）の順に探し、どこにも無ければ不合格。自分の行は重なりに数えない | **見る場所は1か所だけ**（古い枝を足し合わせない）：`--ledger-ref <今の台帳枝>` を渡せばその枝、`--ledger-pr <番号>` を渡せばその PR の差分（自分の行を消しているか。gh が要り、使えなければ不合格）、どちらも無ければ台帳フォルダ。そこに残っていれば不合格。ほかの ledger 枝に残る行は警告だけ。同じBotの別の行は数えない |
| session_id の比べ方 | YAML の値として完全一致（引用符・前後の空白・行末コメントを外す。正規表現・部分一致は使わない）。`--bot` を渡せば `<bot>.yaml` だけを見る。台帳フォルダ・枝・PR で同じ比べ方 | 同じ |
| LLM行のモデル数 | — | 書き手と別のモデルの LLM行が1つ以上あるか（§5-1。特定のモデル名は求めない）。無ければ不合格 |
| 照合の行と記録先 | — | `HH:MM JST \| 照合 \| <照合モデル> \| 合格／指摘N件 \| <記録先>` があるか（複数あれば1行ずつ全部）、照合モデルの LLM行があるか、照合モデルが書き手と同じでないか（書き手＝`--writer-model`、無ければ最初の LLM行のモデル。ほかのモデルの LLM行があっても、書き手自身の照合は数えない）、記録先ファイルがあるか。LLM行は `（T3、照合）` のように用途を併記した形も数える。**既定で不合格**にする。本文の作業でないとき（Grok側など）だけ `--no-verifier <理由>` で警告にする（`--require-verifier` は旧オプションで既定と同じ） |
| 切り離しの検出（`--check-detach FILE`、何度でも） | 不合格 | 不合格 |
| リポジトリ作業（`--output-kind repo`） | `github:<owner>/<repo>/<パス>`（末尾に ` (branch <枝>)` 可）を認める。`outputs/` は禁止のまま。台帳の重なりはリポジトリ名を含む完全一致だけで比べる（末尾3段では比べない） | 同じ。`projects/<案件>` の形と「空でない」は見ない |
| progress.md の先頭行 | `--bot-label` を渡せばその文字列があるか（無ければ不合格）。渡さなければ `--bot` の末尾の識別子（`@tw1` など）があるか（無ければ警告） | — |

切り離し検出の決まり（誤検出を避けるための除外）：

- 見るもの：`nohup`／`setsid`／`disown` という語、単独のアンパサンド（行末・行の途中・閉じ括弧の前のどれでも。例 `sleep 1 & echo done`、`{ cmd & }`、`cmd&#c`）。 <!-- pillars:allow-detach -->
- アンパサンドとして数えないもの：`&&`、`2>&1` などのリダイレクト（`>&`・`&>`・`&>>`）、`|&`、`\&`（文字としてのアンパサンド）。 <!-- pillars:allow-detach -->
- 見ないもの：`pillars:allow-detach` と書いた行（説明文・スクリプト自身・テストの説明用）、行頭が `#` のコメント行、行の途中の ` #` 以降、引用符（`'…'` と `"…"`）の中、`.md` ファイルの ``` か ~~~ で囲んだコードブロックの外（文章で禁止事項を説明できるように）。
- 限界：`bash -c "…"` や `"$(…)"` のように引用符の中に書いた切り離しは見つけられない。引用符で囲まない URL のクエリ（`?a=1&b=2`）は誤検出する（引用符で囲む）。字下げだけのコードブロック（md）は見ない。 <!-- pillars:allow-detach -->

台帳の枝の探し方（「ledger」を名前に含む枝）は検索の条件で、いまの一時的な `ledger/<session>` 枝も見つけるためのもの。公式の枝の名前は `ledger` に決まった（2026-11-27、guard.md §5-2）が、公式枝はまだ無く作り方も未決のため、検索の条件は変えない。

repo 作業の書き方は、台帳 README §9 の `output_dir`（「パスかID」）の ID 側として扱う。実際の台帳の行（`github:5co-hub/template/handoff-… (branch …)`）と同じ形。#1427 の決まり（顧客フォルダ作業は `projects/<案件>/` だけ、`outputs/` は禁止）は変えない。この扱いは §5-3 で決定した。

## 5. 決定（2026-11-27 08:02 JST 若松さん決定、須藤 航@tw1 経由）

### 5-1. 別モデルによる照合の必須範囲 → 案 B を採用

- **決定：本文の作業（コード・図・長文・調べもの）は、すべて書き手と別のモデルが照合する（案 B）。** LLM行のチェックは「書き手と別のモデルが1つ以上」で合格（2モデル以上のうち、書き手以外が1つ以上）。照合モデルは §4.4 の「高度な検証」の列から選ぶ目安（`rules/2026-11-24_t3-harness-relay.md`）。
- **不採用：** A（システム開発だけ）、C（Gemini を必ず1つ入れる。Gemini は照合モデルの候補の1つで任意）、D（同じ作業を2モデルに書かせて突き合わせる）。
- 既存の規定との関係（どちらも落とさない）：
  - 原則（システム開発）：完了報告の前に別系統の Codex が検品する（`.claude/skills/codex-review.md`）。これは今回の照合に数えてよい（書き手と別のモデルである限り）。
  - 開発委譲の例外：Codex がパッチを提案した作業では、適用・テストと別系統の検品は Codex 以外が担う。Codex に「修正案作成」と「最終検品」を同じ文脈で行わせない。この場合の照合モデルも書き手（パッチを書いた Codex）と別にする。
- 反映：postflight は既定で照合を見る（書き手と別のモデルの LLM行・照合の行・記録先ファイル）。ひな形の照合欄は空・「なし」不可。入口スクリプトも照合モデル・記録先の「なし」を認めない。

### 5-2. 機械で止める方法 → まず起動前・完了前スクリプト（A＋入口）。Actions（B）は次の別PR

- **決定：まず起動前・完了前スクリプト（preflight／postflight と入口 `handoff-launch.sh`）で止める（案 A＋入口）。**
- **本PRに Actions は入れない。GitHub Actions での強制（案 B）は次の別PRで扱う。**
- D（入口スクリプト以外から t3 を呼ばない決まり＋起動ログの事後点検）は別途。C（ローカルの git フック）は不採用。
- 範囲外：agy のフック、launch-guard、Rutzbo の設定には触らない・変更案も出さない。

| 案 | 中身 | 扱い |
|---|---|---|
| A＋入口 | 起動前・完了前スクリプトと入口スクリプト | **採用（本PR）** |
| B | PR 上の Actions で postflight（`.github/workflows/` の追加・保護設定） | **別PR（次）** |
| C | ローカルの git フック（pre-commit／pre-push） | 不採用 |
| D | 入口以外から t3 を呼ばない決まり＋起動ログの事後点検 | 別途 |

### 5-3. リポジトリ作業の `output_dir` → 認める

- **決定：リポジトリを直す作業では、`--output-kind repo` と `github:<owner>/<repo>/<パス>`（末尾に ` (branch <枝>)` 可）を認める。** `outputs/` 禁止はそのまま（repo 作業でも禁止）。顧客フォルダ作業の決まり（#1427）は変わらない。

### 5-4. 入口スクリプト → 使えるBotだけ必須

- **決定：`handoff-launch.sh` が使えるBotは必須（t3 は必ずこのスクリプト経由）。** 使えない環境でも、ひな形の固定行（「〔固定〕」の行と見出し）は目で照らす。
- 不採用：全Bot必須（使えない環境があるため）、推奨どまり。

## 6. 限界（正直に書く）

- **毎回読み直す仕組みは完全ではない。** スキルは入口だけで本文を写さない作りだが、バックグラウンドの作業者はスキルを読み直さず、親からの指示文だけで動く。ひな形の固定文と、入口スクリプトが付ける前置きで補うが、作業者が前置きを読み飛ばすことは止められない。
- **入口スクリプトの強制は、このスクリプトを通す運用でだけ効く。** `t3` を直接呼ぶ経路は止められない（Actions による強制は §5-2 のとおり次の別PR）。
- **照合が「十分か」は判定できない。** スクリプトが見られるのは、LLM行のモデル数・照合の行・記録先ファイルがあるかまで。照合の中身は人が見る。
- **台帳の PR の確認は gh に頼る。** gh が無い・未ログインの環境では、未マージの台帳 PR の中の自分の行は確かめられない（警告だけ）。
- 切り離し検出は §4-4 の限界がある。
- **自分の行は Bot と session_id の組で決める。** `--session-id` を渡すときは `--bot` も要る（入口スクリプトでは必須）。別のBotの同じ session_id は自分の行に数えず、重なりからも外さない。
- **`--ledger-pr` は、その PR の差分に自分の行を消す変更（行の削除か、ファイルごとの削除）があるときだけ合格にする。** 追加した PR に削除を積んで差分が無くなった場合は、その PR では確かめられないので `--ledger-ref` か台帳フォルダで確かめる。見るのは `registry/session-ledger/sessions/` 直下の YAML だけ。

## 7. 使い方

```
# 起動（待つ側は Shell ツールのバックグラウンド起動〈block_until_ms 0〉で呼ぶ）
# repo 作業なら --output-kind repo --output-dir github:<owner>/<repo>/<パス>
bash scripts/handoff-launch.sh \
  --task <ひな形を埋めた task.md> --launch-dir <起動場所> \
  --output-dir <起動場所>/projects/<案件> \
  --progress <progress.md> --ledger-dir <bot-orchestration>/registry/session-ledger/sessions \
  --session-id <自分の行の session_id> --provider claudeAgent --model claude-opus-5-5 --option effort=low \
  [--bot-label "<progress.md 先頭行の名前>"] [--check-detach <run スクリプト>] [--dry-run]
# --option の名前はプロバイダごとに違う（antigravity は thought_level。§9）

# PR／DONE の前（#1427 の引数に足す）
bash scripts/pillars-postflight.sh … --session-id <ID> [--ledger-ref <今の台帳枝> | --ledger-pr <番号>] \
  [--writer-model <書き手のモデル>] [--no-verifier <本文の作業でない理由>] [--check-detach <ファイル>] [--output-kind repo]
```
