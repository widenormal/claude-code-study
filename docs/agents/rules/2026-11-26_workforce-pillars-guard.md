## 1. 何が起きたか（事実）と原因

### 1-1. 回し方

- **事実：** 最初の内訳の図4枚を、T3 を通さずに Grok側のバックグラウンド作業者がコードを書いて作った。T3必須化（#1426）より前の作業だが、「本文の作業はT3に回す」原則から外れていた。
- **原因：**
  1. 起動前に「どこで本文を書くか」を確かめる手順が無かった。原則は文章としてあったが、起動の直前に照らす項目になっていなかった。
  2. Grok側が本文を書いたかどうかは、あとから見ても見分けにくい。`progress.md` に「どのモデルで書いたか」を残す行（LLM行）が必須になっていなかった。

### 1-2. 記憶の構造

- **事実：** T3 は AGENTS.md のある `~/work/AI-shelpha` から起動した（ここは守れた）。ただ、成果物を `projects/<案件>/` ではなく `outputs/…/` 配下に置いた。決めたことを memory の `<bot>.md`（担当者別の active-context ファイル）と `decisions.md` にも書いていなかった。
- **原因：**
  1. AI-shelpha には歴史的に `outputs/` と `projects/` の両方がある。どちらが正か、取り次ぎの指示文に書かれていなかった。
  2. DONE の条件に「memory へ書き戻した」が入っていなかった。書き戻しは AGENTS.md に必須とあるが、DONE の前に照らす項目になっていなかった。

### 1-3. 全社セッションマネジメント（台帳）

- **事実：** 台帳を読み、自分の行を足し、終わって消した（手順は守れた）。ただ、その変更の PR（bot-orchestration #28〜#32）が未マージのため、作業中はほかのBotから行が見えなかった。
- **原因：** 台帳の書き込みを main に反映する経路が決まっていない（README §10-1 が未決）。PR を出しても、マージは若松さんの確認待ちになるため、作業時間（数十分〜数時間）の間に main へ入らない。読む側も main しか見ていない。

## 3. 回し方

**決定（2026-11-26 若松さん決定（須藤 航@tw1 経由））：** 下の 3-1・3-2 の人の決まり（チェック項目）は全Botの必須。スクリプト（preflight／postflight）は使えるBotだけ走らせ、不合格なら起動しない／DONE にしない。スクリプトが使えない環境（共有ドライブだけで作業するBotなど）でも、項目は目で照らす。

### 3-1. 起動前チェック（取り次ぐBotが、起動の直前に確かめる）

人の決まり（全Bot必須）：

1. **T3 を使うか。** 本文の作業は T3。CLI に落とすときは、起動前に `progress.md` へ `HH:MM JST | 切替 | <理由>` を1行書く（§6.2 の形式）。
2. **起動場所に AGENTS.md があるか。** `test -f <起動場所>/AGENTS.md`。無ければ起動しない。
3. **`progress.md` があり、先頭行にBot名があるか。**
4. **LLM行を書く手順が指示文に入っているか。** `HH:MM JST | LLM | <モデル名>（T3）`（CLI なら `（CLI）`）。
5. **本文を Grok側が書く計画になっていないか。** 指示文の「やること」に、Grok側の作業としてコード・図・長文・調べものが入っていないかを目で確かめる。Grok側に残すのは、コマンド実行、duckdb での数の集計、git push、返ってきた要約の確認だけ（§4.0）。

スクリプト（`pillars-preflight.sh`）で確かめること：2・3、`progress.md` に CLI の行があるならその行に理由が書いてあるか、台帳（§5-1）。4・5 は指示文の書き方の問題なので、スクリプトでは確かめない（`progress.md` はまだ空に近いため）。

### 3-2. PR／DONE 前の自己チェック

人の決まり（全Bot必須）：

1. `progress.md` に LLM行があるか。
2. 最後の行が `DONE` か。
3. 成果物が正しい場所（`projects/<案件>/`）にあるか。
4. PR本文に LLM行をそのまま載せたか。

スクリプト（`pillars-postflight.sh`）で確かめること：1・2・3。4 は PR本文が手元にあるときだけ `--pr-body` で確かめる（無ければ確かめない）。

### 3-3. 「Grok側が本文を書いていないか」は自動では判定できない

- **判定できない理由：** 同じ git の作者名・同じフォルダで、Grok側と T3 側のどちらがファイルを書いたかは、ファイルの中身からは見分けられない。
- **代わりに見るもの（案。どれも「書かれていない」ことの証明ではなく、抜けを見つけるための目印）：**
  1. `progress.md` に LLM行があり、モデル名の後ろが `（T3）` か。`（CLI）` なら、その前に切替の理由の行があるか。
  2. `progress.md` の区切りの行が、取り次ぎ先の作業時間の中にあるか（成果物の更新時刻より前に、取り次ぎ先の「起動」の行があるか）。
  3. 本文の差分が、取り次ぎ先の作業の中で作られたコミットに入っているか（取り次ぎの指示で「コミットまで」を取り次ぎ先にやらせた場合）。取り次いだBotのコミットに本文が入っていたら、確かめ直す。
  4. T3 の起動記録（スレッド ID など）が `progress.md` か取り次ぎフォルダに残っているか。
- 1 と 2 はスクリプトで見られる（1 は postflight、2 は人が見る）。3 と 4 は人が見る。

## 4. 記憶の構造

### 4-1. 成果物の置き場所（決定：禁止）

| 案 | 中身 | よい点 | 弱い点 |
|---|---|---|---|
| 禁止（採用） | 成果物は最初から `projects/<案件>/` だけに置く。`outputs/` などには置かない | 移し忘れが起きない。チェックが単純（`projects/` 以外の新規ファイルは不合格） | 既存の `outputs/` に依存する古いスクリプト・手順がある場合、その手順を直すまで使えない |
| 一時置きのみ（不採用） | `outputs/` などには作業中だけ置き、DONE までに `projects/<案件>/` へ移す | 古い手順をすぐには直さなくてよい | 移し忘れが起きやすい（今回の事例がまさにこれ）。DONE の前に毎回確かめる手間がある |

**決定：禁止（2026-11-26 若松さん決定（須藤 航@tw1 経由））。** `outputs/` などの別の場所は、一時置きも不可。理由：今回の事例は「どちらに置くか決まっていなかった」ことから起きた。一時置きを許すと、移し忘れという同じ形の抜けが残る。台帳 README §3 も「成果物は `projects/<案件>/`」とだけ書いている。

- postflight は、`git status` で見える範囲で、`outputs/` などの決めた名前のフォルダに新しいファイル（未追跡または追加）があれば不合格にする。既に追跡済みのファイル（昔からあるもの）は見ない。
- 既に `outputs/` にある昔の成果物の直し方は §4-3（新しく置くことは認めない）。

### 4-2. DONE の条件に書き戻しを入れる

DONE の前に、次の2つへ書く（案）：

- `memory/active-context/<担当者>.md`（担当者別の active-context ファイル。リポジトリの決まりでは `<bot>.md` 相当）
- `memory/decisions.md`（決めたことがあるとき。無ければ「決定なし」と active-context に書く）

書く内容の目安：

1. 何を決めたか（1〜3行）
2. どこに置いたか（`projects/<案件>/` のパス）
3. 次に何をするか

**数値・ASIN・顧客データ・Shelpha のデータは書かない。** AI-shelpha の AGENTS.md も「数値は伏せて記録」としている。

postflight は、`git status` と、引数で渡した基準のコミット（`--base`）からの差分の範囲で、この2つのファイルに変更があるかを見る。中身が十分かは判定しない。

### 4-3. 既に起きた事例（成果物が `outputs/` 配下にある）への直し方

順番（案）。**消す作業そのものは今回しない。**

1. 元のファイルは消さない。
2. `projects/<案件>/` へコピーする。
3. コピーした先を開いて、元と同じか確かめる（ファイル数とハッシュの照合）。
4. `memory/active-context/<担当者>.md` と `memory/decisions.md` に、置き場所を書く（数値・ASIN は書かない）。
5. 元のファイルの整理（消す・残す）は、担当者と若松さんの確認のあと。

## 5. 全社セッションマネジメント（台帳）

### 5-1. 読む側の策 D（当面併用と決定。preflight に入れた）

- preflight は、引数で渡した台帳フォルダ（`sessions/*.yaml`）を読み、**同じ `output_dir` で状態が「進行中」または「停止」の行**があれば不合格にする（README §5-3 と同じ判定）。
- 台帳が見えない問題の暫定策として、`gh pr list`（読み取り）で bot-orchestration の open な PR のうち `registry/session-ledger/sessions/` を変更しているものを一覧で出す（警告として標準エラー）。`gh` が無い／未ログインなら警告にとどめて止めない。
- この策は「未マージの行がある PR がある」ことを知らせるだけで、その PR の中の `output_dir` までは比べない（中身まで読むかは §5-2 の案 D の拡張として残す）。

### 5-2. 未マージで見えない問題の解決案（決定：B＋当面 D）

前提：GitHub Actions の予算は月 $20（取り次ぎ指示の前提。決定の正本はこの文書では未確認。円換算は約3,000円〈1ドル150円で換算・推測〉）。`bot-orchestration` には、いま自動テストが無い。

| 案 | やり方 | よい点 | 弱い点 | 必要な権限・設定 | 予算・前提への影響 |
|---|---|---|---|---|---|
| A（不採用） | `sessions/<bot>.yaml` だけを変える PR を、自動チェック（変更パスが `sessions/` の自分のファイルだけか）に通ったら自動マージする | main が正のまま。他の変更は今までどおり確認後マージ。履歴が PR に残る | 「mainへのマージは若松さんの確認のあと」の例外になる。自動テストを新しく作る必要がある。マージまで数分の遅れ | リポジトリの auto-merge 有効化、Actions の追加、マージ権限を持つトークン、保護設定の調整（藤村さん） | Actions を新しく使う（台帳の更新1回ごとに1回）。月の回数しだいで予算に効く |

| D（当面併用） | 読む側の暫定策。起動前に open PR の台帳変更も読む（§5-1、preflight に入っている） | いますぐ使える。権限の変更なし | 書く側の遅れは直らない。PR を出していない枝の変更は見えない。`gh` が使えない環境では見えない | 読み取りの `gh` ログインだけ | 影響なし |
| E（不採用） | 台帳を共有ドライブに置く | git を使わないので反映が即時 | README §2 の置き場所（git の `sessions/`）と食い違う。§3 の「当面は共有ドライブだけを正とする」は**ハーネスと成果物の置き場所**についての決定で、台帳の置き場所の決定ではない。同時に書いたときの衝突の扱いが別に要る | 共有ドライブの書き込み権限（各Bot） | 影響なし。ただし台帳 README の設計を変える大きな変更 |

**決定：B を採用し、当面は D を併用する（2026-11-26 若松さん決定（須藤 航@tw1 経由））。** A（自動マージ）と C（main への直接 push）は不採用。理由：「mainへのマージは若松さんの確認のあと」という既存の決まりを変えずに反映を即時にでき、Actions の予算も使わないため。
- この決定では、保護設定（main・台帳専用の枝とも）の変更は行わない。
- 台帳専用の枝の名前は `ledger`（2026-11-27 13:47 JST 若松さん本人の決定）。公式の `ledger` 枝はまだ作らない（作業用の `docs/…` 枝や一時的な `ledger/<session>` 枝は公式の `ledger` 枝ではない）。
- まだ案のもの：台帳専用の枝の作り方・枝の保護の要否（藤村さんと相談）、D をいつやめるか。読む側の切り替えは preflight の `--ledger-dir` を台帳専用の枝の作業コピーに向けるだけで済む見込み（推測。枝ができてから確かめる）。

## 6. スクリプトの使い方

```
# 起動前（取り次ぐBotが走らせる）
bash scripts/pillars-preflight.sh \
  --launch-dir <起動場所> \
  --output-dir <起動場所>/projects/<案件> \
  --progress <progress.md のパス> \
  --ledger-dir <bot-orchestration>/registry/session-ledger/sessions \
  [--bot <姓@tw1>] [--no-gh]

# PR／DONE の前
bash scripts/pillars-postflight.sh \
  --launch-dir <起動場所> \
  --output-dir <起動場所>/projects/<案件> \
  --progress <progress.md のパス> \
  --bot-memory <起動場所>/memory/active-context/<担当者>.md \
  --decisions <起動場所>/memory/decisions.md \
  [--ledger-dir <…/sessions> --bot <姓@tw1>] [--base <基準のコミット>] [--pr-body <PR本文の md>] \
  [--scratch-dirs "outputs out tmp"]
```

- リポジトリ作業（`--output-kind repo`）・自分の台帳行（`--session-id`）・照合・切り離し検出・入口スクリプトは `rules/2026-11-27_workforce-pillars-enforce.md` §4・§7 を参照（第2弾・案）。
- どちらも読み取りだけ。`git status` と `git diff --name-only` と `gh pr list` 以外のコマンドで、リポジトリやファイルを変えない。
- 台帳の YAML は、行頭の `- employee:` ごとに1行として読む簡易な読み方（yq や Python のライブラリに頼らない）。台帳の雛形（`sessions/example-bot.yaml`）の形を前提にしている。

## 7. 用語

| 言葉 | 意味 | 出どころ |
|---|---|---|
| 本文の作業 | コード・図・長文・調べもの | `rules/2026-11-24_t3-harness-relay.md` §4.0 |
| Grok側 | 会話本体とバックグラウンド作業者 | 同 §4.0 |
| LLM行 | `progress.md` に書く `HH:MM JST | LLM | <モデル名>（T3/CLI）` の1行 | 取り次ぎ指示の固定形式（本文書 §0） |
| 台帳（セッション台帳） | `registry/session-ledger/sessions/<bot>.yaml` | bot-orchestration `registry/session-ledger/README.md` §0・§2 |
| `output_dir` / `launch_dir` | 成果物を置く場所 / LLM が cd する場所 | 同 README §3・§9 |
| auto-merge（自動マージ） | 必要な条件を満たしたら PR を自動でマージする GitHub の機能 | https://docs.github.com/en/pull-requests/collaborating-with-pull-requests/incorporating-changes-from-a-pull-request/automatically-merging-a-pull-request |
| 保護設定（ブランチ保護ルール） | 枝への直接 push やマージの条件を決める GitHub の設定 | https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches |
| preflight / postflight | この文書で足すスクリプトのファイル名（起動前／完了前のチェック）。一般用語として使わない | 本文書 §2 |
