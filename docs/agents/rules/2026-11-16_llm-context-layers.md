### 1-1. ① 全Bot共通

**置き場所（既存を使う。新設しない）**

- 入口と本体：`/workspace/knowledge/agents/AGENTS.md`（現状 129行）
- 詳細の正本：`/workspace/knowledge/agents/rules/<YYYY-MM-DD>_<件名>.md`（現状 6ファイルが正本）

**推奨：AGENTS.md は「短い本体＋索引」にする（索引だけにはしない）**

- 理由：AGENTS.md は現在、全Botが `cat /workspace/knowledge/agents/AGENTS.md task.md | claude -p …` の形で**毎回まるごと標準入力に渡している**（`/workspace/knowledge/agents/AGENTS.md` (c)節、`/home/box/agent-data/workflows/claude-codex-cli/SKILL.md` 手順1〜4）。索引だけに変えると、いま届いている共通手順が届かなくなる。今回の問題は「届いていないものを増やす」ことなので、届いているものを減らす変更はしない。
- 足すのは1節だけ：末尾に「### 決まりの正本（索引）」を置き、`rules/` の各ファイルを**1行ずつ**並べる。本文は複製しない。
- `rules/` の日付付きファイルは**①の詳細として残す**（正本。移動・統合しない）。

**書式（1ファイルの構成）**

```markdown

- 層：①全Bot共通
- 状態：決定 ＝ 2026-11-16 16:18 JST 若松さん承認／または「案（承認待ち）」
- 出典：<どの会話か。例：汐見さんのチャット、WEBディレクターのチャット>
- 関連：<他の正本の絶対パス>

要約：（3〜5行。原文の全文は貼らない）

## やり方
1. …

## 変わらないこと
- …

## 変更記録
- 2026-11-16 追加（反映者：<Bot名>）
```

## 3. 若松さんの決定をmdへ反映する手順

### 3-1. 誰が

- **原則：若松さんの発言を直接受けたBotが、その場で下書きする。** 伝聞で書かない。
- 層ごとの担当：
  - ①全Bot共通 → KR-1B AI組織図（汐見）が `rules/` に書く（既存の `rules/` を作ってきた担当と同じ）。
  - ②リポジトリ・Botごと → そのリポジトリの担当Bot（corporate-website なら真鍋）。
  - ③作業の種類ごと → その作業の担当Bot（人物写真ならフォトディレクター、サイト実装なら真鍋）。迷ったら②の担当。
- **配布（他リポ・全Botへの展開）は Template（榊さん）だけ。** この手順の外。
- 対象Bot本人が決定を受けた場合も、本人が書く。汐見に投げ直して遅らせない。

### 3-2. いつ

- **決定の当日中（JST 24時まで）に、該当mdへ1行追記する。** 完成した文章にしなくてよい。1行でも書いてあれば次の取り次ぎで届く。
- 当日中に書けないときは、`01_message.md` の「今回とくに守ること」に書いて取り次ぎ、**翌営業日の午前中まで**にmdへ移す。
- 配布・周知を待ってから書く、はしない（待っているあいだに今回と同じ漏れが起きる）。

### 3-3. どこへ（判断の目安）

| 決定の性質 | 層 | 置き場所 |
|---|---|---|
| 全Botに効く（LLMの使い分け、取り次ぎ方、禁止事項） | ① | `/workspace/knowledge/agents/rules/<YYYY-MM-DD>_<件名>.md` ＋ AGENTS.md の索引に1行 |
| 1つのリポジトリ／1つのBotだけに効く | ② | `<リポ>/CLAUDE.md`（短く）または `<リポ>/docs/site-rules/README.md` |
| 特定の作業の種類に効く（写真、記事、公開手順） | ③ | `<リポ>/docs/site-rules/<種類>.md` |
| いまの状況・進行中のこと（決まりではない） | ② の状態 | `<リポ>/memory/active-context.md` |

- **迷ったら③に書く。①には書かない。** ①は全Botが毎回読む（＝毎回トークンを使う）ので、入れるのは本当に全員に効くものだけ。
- ①か③か判断がつかないときは、③に書いて、①の索引に「③にある」とは書かない（索引が膨らむ）。②の `README.md` からたどれれば足りる。

### 3-4. 書く内容（4つだけ）

1. **決定の日時（JST）**：`2026-11-09` のように日付。時刻が分かるなら `HH:MM JST` も。
2. **原文の要約**：1〜2行。命令形で書く。**原文の全文を長いまま貼らない。**
3. **出典**：誰の指示か＋どの会話か（例：「若松さん（WEBディレクターのチャット）」）。記録があればその絶対パスと節名。
4. **適用範囲**：いつ適用されるか（例：「サイトに人物の画像を置く・差し替えるとき」）。

### 3-5. 線引き（書かないもの）

- 秘密の値（パスワード・APIキー・トークン・Cookie）。1Passwordの項目名だけ。
- 人事・給与・評価・面談の中身。
- 覚書などで扱う場所が限られているデータ（決められた端末の外に出さないもの）。
- Shelpha の数値・推計手法・データ元。データ元として書くときは「Shelpha」と書く（別名は書かない）。
- 顧客名・仕入れ先名。
- **幹部のみ公開の情報（特定の個人の所属や役職を含む）は、社員向け・全Bot向けのmdに書かない。**役職や社外向け資料の例としても書かない。
- 幹部向けに置く必要がある決定は、**社員向けと同じファイルに混ぜない**。別のファイル・別の置き場所にする。置き場所は若松さんに指定してもらう（決定事項6-7）。この案では置き場所を勝手に決めない。
- 判断できないときは書かずに、若松さんに「どこへ置くか」を1行で聞く。

### 3-6. 反映したことをどう残すか

- **各mdの末尾に「## 変更記録」を1〜2行だけ**。形式：`- 2026-11-16 <何を> 追加／変更（反映者：<Bot名>）`
- 新しい台帳・一覧・ダッシュボードは作らない（増やすと更新されずに腐る。`memory/active-context.md` が 11-09 で止まっているのが実例）。
- `memory/decisions.md` がすでに決定の履歴なので、②③の決定はそこにも1節を書いてよい（既存の運用どおり）。③には要約と、decisions.md の節名だけを書く。

### 3-7. 「Grokの記憶だけに残してmdに書かない」を繰り返さない最小の手順（4行）

1. 若松さんの決定を受けたら、**その場で層を1語で言う**（①／②／③）。

**この手順の外（別に若松さんの承認が必要）**：全Botへの配布、他リポへの展開、Template の正本の変更、送信・投稿、`main` への反映、本番公開。

やること：当日中に1行書く。出典を書く。
やらないこと：原文の全文を貼る。新しい台帳を作る。幹部限定の情報を社員向けmdに混ぜる。承認前に配布する。

## 8. 一発で合格させるための取り次ぎと学び

**若松さんの追記（2026-11-16 16:54 JST）：「取次ぎ先のLLMが合格の成果物を出せなければ、結果的に時間とトークンを失います。」**

§目的 を、取り次ぎの手順に落とす。4つ。

### 8-①. 取り次ぐ前に、合格条件（受け入れ基準）を指示文に必ず書く

**どこに書くか**

| 渡す形 | 書く場所 |
|---|---|
| 指示文（`task.md`） | **冒頭の「読む層」の直後**。①②③のパスの次に「合格条件」を置く（相手が読み始める前に、何が合格かを見せる） |
| `01_message.md` | 「読む層」の行の次に1行 `- 合格条件: …`。§2-3(1) と同じく、行数が苦しいときは「依頼」の行末に畳む（行を増やさないのは既存ルールどおり） |
| `02_summary.md` | §2-3(2) の「適用される決まり（読む層）」節の末尾に `- 合格条件: `（1〜3行） |
| ③層の各md | その作業の種類に**毎回**効く合格条件は、③の「## 機械で確かめること」「## 人が確かめること」に置く（§1-3 の書式どおり）。指示文には「③の1・3が合格条件」と番号で指すだけでよい（本文を複製しない） |

**書き方**

満たせたかどうかが、**機械か目視で判定できる形**にする。「きれいに」「適切に」「いい感じに」は合格条件にならない。

例（corporate-website の人物写真。§0・§1-3 の実例をそのまま使う）：

> 合格条件（3件。全部満たすこと）
> 1. ヒーロー／Oracle の前に置く人物画像は、**背景が透明**（アルファチャンネルあり）であること。背景付き（`composite` / `*_scene`）を Oracle の前に置かない。根拠：③`/workspace/corporate-website/docs/site-rules/person-photo.md` の1（決定 2026-11-09 若松さん／記録 `memory/decisions.md`）
> 2. 機械の確認：`npm run build` が通ること（透過チェックを含む。§4-A）。落ちたまま提出しない。
> 3. 人の確認：③の「## 人が確かめること」の2項目（切り抜きの輪郭に白い縁が残っていないか／同じページで人物の大きさ・目線の高さが揃っているか）を**自分で記入**して出すこと。
> 提出物：下書きPR（タイトルに【試行・マージ保留】）＋ 上の1〜3の結果。`main` へのマージと本番反映はしない。

**チェックに入れる**

- **合格条件が書けていない取り次ぎは送らない**（§7-2 の5番のチェック項目）。
- 自分で合格条件を書けないときは、送る前に若松さんか②の担当Botに1行で聞く。**「とりあえず送って、出てきたものを見て決める」はしない。** それが差し戻しの作り方である。

### 8-②. 取り次ぎ先のLLMが、提出前に自分でチェックリストと自動テストを通す

**機械で確かめられるもの**

- 提出前に**自分で走らせ、結果を報告する**。corporate-website なら `npm run build`（公開用語・記事と人物の一致・透過の3〜4本が1回で走る。§4-A）。
- 報告の形（1行ずつ）：実行したコマンド／終了コード／落ちた項目（あれば）。
- **走らせていないなら「未実行」と書く。通ったことにしない。**
- 落ちたまま提出しない。直してから再実行する。直せないときは `BLOCKED | 理由` を書いて止まる（Codex の `progress.md` の既存ルールと同じ形）。

**機械で難しいもの**

- ③層の「## 人が確かめること（Claude Code レビュー）」のチェックリストを、**提出前に自分で記入**する（満たしたものは `- [x]`、満たせていないものは `- [ ]` のまま理由を1行）。
- 記入したものを提出物に添える。**空欄のまま出さない。**

**明記**

- **「提出してからレビューで初めて確かめる」だけにしない。** レビューは最後の網であって、1枚目の網ではない。1枚目は作った本人が通す。
- レビュー側の役割は変えない：Claude Code がするのは指摘と修正案まで。**承認・マージ・公開は若松さん（または所定の承認者）**（§4-B）。
- **自己チェックが通ったことも承認ではない。** 合格条件を満たしたという申告であって、レビューと承認は従来どおり行う。

### 8-③. 差し戻し回数と原因を記録し、多い決まりを3層mdや自動テストに足していく

**原因の区分（3つだけ。増やさない）**

| 区分 | 意味 | 直す先 |
|---|---|---|
| A 決まりの見落とし | 決まりは届いていた（パスも合格条件も書いてあった）が、守られなかった | 機械で確かめられるなら**自動テストに足す**。難しければ③の書き方を直す（番号で指す・条件を判定できる文に直す） |
| B 指示不足 | 合格条件が書いていない／読む層のパスが無い／③にその決まりがそもそも無い | 取り次ぎ側の手順（§7-2）と、③のmdに1行追記 |
| C その他 | 上のどちらでもない（素材が無い、前提が変わった、相手の実行環境で動かなかった など） | 個別に対応。mdも自動テストも増やさない |

**記録の置き場所（新しい重い台帳は作らない）**

- 試行中は**1ファイルだけ**：`/workspace/llm-context-layers/out/rework-log.md`（この作業フォルダの中。リポジトリもテンプレも触らない）。
- 1件1行。形式：`YYYY-MM-DD HH:MM | 案件 | 回し先LLM | 差し戻し回数(通算) | 原因区分(A/B/C) | 決まりの番号または一言`
- 例：`2026-11-16 17:10 | corporate-website 人物写真 | CDX | 1 | B | ③person-photo.md が未作成で合格条件を書けなかった`
- 試行が終わったら、この1ファイルを §5 手順2 の実測として出す。**ダッシュボードも一覧ページも作らない**（更新されずに腐る。`memory/active-context.md` が 2026-11-09 で止まっているのが実例）。
- 恒久の置き場所（案。試行後に若松さんが決める）：③層の各mdの「## 変更記録」に、**足した決まりだけ**を1行残す。差し戻しの生ログは残さない。

**「多い」の判断**

- 目安（案）：試行期間（5営業日）のうち、**同じ決まりで2件以上**、または**同じ原因区分で3件以上**。
- この2件・3件という数字は目安で、**根拠となる過去の実測はない（未計測）**。若松さんが別の線を決めるならそれに従う。

**md・自動テストへの追加手順**

1. 機械で確かめられるなら、**まず自動テスト**（人の注意に頼らない）。③のmdには1行だけ書いて、テストのファイル名を指す。
2. 機械で難しいなら、③のmdの「決まり」に1行＋「人が確かめること」に1項目。
3. 全Botに効くと分かったときだけ①（`rules/`）。迷ったら③（§3-3）。

- **誰が**：③は作業担当Bot、②はリポ担当Bot、①は汐見（§3-1 と同じ）。
- **承認はいつ**：
  - ③のmdへの1行追記は、**試行の作業ブランチ上なら担当Botが入れてよい**（§5「触ってよいもの」の範囲内）。
  - 自動テストの新設・`npm run build` や CI への連結は、**若松さんの承認後**（決定事項6-5・6-6と同じ件）。
  - ①への追加、テンプレへの反映、他リポ・全Botへの展開は**若松さんの承認後**。配布は Template（榊さん）。

### 8-④. 差し戻しにかかったトークンと時間を測る指標（案）

- 試行の件数は少ない（5営業日・corporate-website のみ）。割合を書くときは**件数も併記する**（例「一発合格率 3/5」）。母数の小さい割合だけを報告しない。
- 時間は分単位でよい。秒まで測るための仕組みは作らない。
