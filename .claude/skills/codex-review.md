# Skill: Codex セカンドオピニオン（GPT-5 系）

> Claude が「実行する側」、Codex が「判断する側」。
> 戦略・設計・リスクチェックの最終確認と、行き詰まったデバッグの委譲に使う。
> モデル既定値は `scripts/llm-models.conf`（申請制で自動更新）が正。

## トリガー

- 「Codex に聞いて」「セカンドオピニオン」「これでいいか？」
- 設計レビュー: アーキ判断、API 設計、DB マイグレーション安全性
- 戦略相談: SEO 改善、ローンチ準備、交流会の優先順位
- リスクチェック: 800 人講座のような大規模イベント前の網羅的チェック
- デバッグ委譲: Claude が2回修正しても直らない不具合（下記「デバッグ委譲」節）

## 実行コマンド

```bash
# 単発質問
bash scripts/codex-call.sh "この PR の設計でリリース判断していいか？" < diff.txt

# 戦略相談（system 上書き可）

# モデル切替（重い判断はフラッグシップ = conf の CODEX_FRONTIER_MODEL）
bash scripts/codex-call.sh --frontier "DB マイグレーション 0042 の安全性を確認"
```

## デバッグ委譲（エスカレーション型）

「デバッグ＝常に Codex」ではなく、行き詰まりの段階で委譲する。根拠は Claude Code
チーム公式の loops ガイド「レビューは文脈を持たない第二エージェントに（fresh
context はバイアスがない）」と、公式モデル位置づけ（Terra=日常デバッグ／Sol=難所）。

1. **一次対応 = Claude Code**（文脈を持っている側が最速）
2. **Claude が2回修正しても直らない／症状と原因が離れている**
   → Codex に委譲。既定モデル（conf の `CODEX_DEFAULT_MODEL`）で:
   ```bash
   bash scripts/codex-call.sh "この不具合の根本原因を特定して最小の修正案を出して" < 再現ログ.txt
   ```
3. **複数コンポーネント横断・並行処理/競合・CI でのみ失敗・根本原因不明**
   → `--frontier`（conf の `CODEX_FRONTIER_MODEL`）に昇格:
   ```bash
   bash scripts/codex-call.sh --frontier "再現手順と関連コードを添付。競合状態の可能性を含め根本原因を特定して" < context.txt
   ```
   codex CLI が入っている環境ではリポ探索込みの委譲が上位互換（read-only で安全）。
   **`timeout` を必ず前置する**（理由・禁則は「背景実行と待機の禁則」節）:
   ```bash
   timeout 1200 codex exec --sandbox read-only "テスト X が CI でだけ落ちる。根本原因を調査して"
   ```
4. **完了条件は決定論で渡す**（「対象テストが green」「再現スクリプトが exit 0」）。
   「直った気がする」で止まるのを防ぐ。Codex の指摘は鵜呑みにせず、
   **採用／却下（根拠付き）／延期／未検証** の4分類で処理して Claude 側で検証する

## 開発委譲の例外規定（2026-07-16 制定・sol 自身の裁定込み）

> **原則として Claude が実装し Codex が独立検品するが、完了条件と変更境界が決定論的な
> 例外タスクでは、Codex は read-only 環境でパッチ提案まで行い、保護された経路での適用・
> テストおよび別系統による検品は Codex 以外が担う。**

- **委譲してよい類型**: ①再現テストがある難航バグ（原因仮説→最小修正案の順で依頼）
  ②外部仕様・副作用・互換性条件が列挙できる単発モジュール ③失敗系・敵対的テストの追加
  ④シェル/CI/git 周りの境界条件 ⑤仕様固定の比較実装（高リスク部品のみ・採用案の検品は
  比較に参加していない別コンテキストで）
- **委譲しない類型**: 要件が曖昧な機能・広範なリファクタ・認可/デプロイ/秘密情報の直接変更
- **運用上限**: 1回 15〜20 分で hard timeout（自動再試行禁止）・原則2成果物・最大3往復。
  超えたらタスク境界が曖昧＝Claude 側に戻す。sandbox 初期化失敗は成果失敗として扱う。
  **hard timeout は宣言ではなくコマンドで担保する**＝`timeout 1200 codex exec ...` /
  `timeout 1200 bash scripts/codex-call.sh ...` の形で必ず前置する（`timeout` の無い
  codex 呼び出しは規約違反。実装手段のない上限は守られず、実際に無限待機を招いた）
- **長いプロンプトは応答が返らないことがある（2026-07-26 実測）**: 3.4KB / 16KB / 40KB の
  プロンプトで timeout 計4回（最大23分・出力ゼロ）。一方 100〜300字なら**5秒前後で応答**する。
  同一セッション内で 4.7KB が17秒で返った例もあり**閾値は不定**なので、長さで安全圏を狙わない。
  - **回避策**: 諮問は**問いを1つずつ短文に割る**。設計相談なら「前提3行＋問い1つ＋『N行で』」に圧縮する
  - **診断順序**: timeout を見たら「使用不可」と判断せず、まず極小プロンプト（例 `"OK とだけ答えて"`）で
    疎通を確認する。疎通が通るなら原因は長さであり、鍵・残高・egress ではない（R7 の適用例）
  - **出力は必ずファイルへ**（`> out.md`）。tool の出力上限で末尾しか読めず、諮問結果を失う事故が実発生した。
    ただし**リダイレクトは起動と同時に 0 バイトのファイルを作る**。「出力ゼロで死ぬ」失敗モードと
    組み合わさると「ファイルはあるが中身は永久に空」になるため、**ファイルの出現・非空を
    完了検知に使ってはいけない**（下記「背景実行と待機の禁則」）
- **適用時の注意**: パッチは盲目的に `git apply` せず対象パス・symlink・権限変更を確認。
  テスト成功と設計妥当性を混同しない。Codex に「修正案作成」と「最終検品」を同じ文脈で
  行わせない（検品は別会話・別系統）
- **Codex CLI の直接書き込みは原則禁止**（保護フックは Claude のツール呼び出しのみ検査
  ＝ガードレール外になるため。同等の保護・監査が整うまで read-only 限定）

## 背景実行と待機の禁則（2026-08-13 制定・実障害由来）

codex は数分〜十数分かかるため背景実行したくなるが、**素朴な待機ループは終了しない**。
実際に本番セッションで残留シェル4本（codex 本体2＋待機ループ2）を発生させた。

**禁止**——ファイルの非空を終了条件にするポーリング:

```bash
# ❌ 絶対に書かない。codex が出力ゼロで死ぬと永久に回り続ける
codex exec ... > out.md &
until [ -s out.md ]; do sleep 5; done
```

`> out.md` は codex 起動と同時に 0 バイトの `out.md` を作る。`[ -s ]` は
「存在 **かつ** サイズ > 0」なので、codex が stdout に何も書かなければ条件は永久に成立しない。
そして「最大23分・出力ゼロ」は上節に記録済みの**既知の失敗モード**である。

**原則**——codex は前景で `timeout` 付きで実行する。待機ループは要らない:

```bash
timeout 1200 codex exec --sandbox read-only "..." > out.md 2> err.log; echo "exit=$?"
```

`exit=124` なら timeout による打ち切り（＝成果失敗として扱い、自動再試行はしない）。

**どうしても背景実行する場合**の必須条件（3つすべて）:

1. `timeout` を必ず前置する（背景でも省略しない）
2. 待機は `wait <PID>` でプロセス終了を待つ。**ファイルの状態を条件にしない**
3. ループを書くなら反復回数の上限を持たせ、上限到達時は必ず抜けて報告する

```bash
timeout 1200 codex exec ... > out.md 2> err.log &
CODEX_PID=$!
wait "$CODEX_PID"; echo "exit=$?"
```

**セッション終了前に `/bashes` で残留シェルを必ず回収する。**
背景シェル自体はトークンを消費しないが、放置は無限ループの温床であり、
`BashOutput` で拾った出力は以降の全ターンでキャッシュ読み込みとして課金される。

## 完成時検品（システム開発の完了ゲート）

システム開発タスクで「完成しました」と報告する**前**に、別系統の Codex による
検品を通す（CLAUDE.md 自己検証ルール2「完了報告は実証ベース」の開発版）。
作った本人（Claude）に「これでいい？」と聞いても自分の成果物には甘い——
fresh context の別モデルが検品する。

- **PR がある開発**: draft → ready 化（または「検品」ラベル付与）で
  `.github/workflows/codex-inspection.yml` が自動発火し、検品結果を PR コメントに投稿
- **セッション内で完結する開発**: 完了報告の前に手動で:
  ```bash
  . scripts/llm-models.conf && timeout 1200 codex exec review --base origin/main -m "$CODEX_FRONTIER_MODEL"   # CLI がある環境（リポ探索込み）
  timeout 1200 bash scripts/codex-call.sh --frontier "完了条件との照合・エッジケース・実装方針の妥当性を検品" < diff.txt
  ```
- 検品観点: ①当初の完了条件をすべて満たすか（未実装の完了宣言がないか）
  ②敵対的視点（エッジケース・エラー処理・セキュリティ境界・そもそもの方針）
  ③検証の実在（tests/lint が実際に通った証跡）
- 指摘は**採用／却下（根拠付き）／延期／未検証**の4分類で処理し、鵜呑み採用しない
