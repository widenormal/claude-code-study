# 図・イラスト（figs）規定 — v3.10（2026-09-29 制定）

> 完成した CI デッキに、内容の理解を助ける図・イラストを足すときの規定。
> 由来＝自社OKR会「育成者の育成カリキュラム」デッキ（2026-09-29・29枚）で、17ページの図を10エージェントで並列制作し、
> WISDOM サイクル図を4案のデザインコンペで決めた運用の正典化。
> 道具は `ci_figs.py`（差し込み・検品・ページ単位プレビュー）と `workflows/`（マルチエージェントの型）。

## 0. 既定＝指示が無くても図を使う（最重要）

- **本文ページには原則すべて、図を1つ置く**。図＝内容に合う**フレームワーク図・グラフ**（`ci_frameworks.py`／129種 SLIDE-PATTERN・型選びは `framework-recommend` スキル）か、理解を助ける**イラスト**（本書・`ci_figs.py`）。
  利用者から「図を入れて」と言われなくても入れる。**文章と表だけのページを作らない**。
- 優先順位：①主張・数値・比較の構造がある → フレームワーク図・グラフ（V3.2_FORMAT「フレームワーク図」）／②構造図が合わない・概念や場面を伝えたい → イラスト（本書2〜5章）／③表が主役のページ → 表の下の余白にイラストを添える。
- 例外（表だけで足りる付録・出典一覧など）は、その `section` に `data-fig-exempt="理由"` を付けて明示する。黙って図を省かない。
- **仕上げ前に `ci-gates.sh` の「図の無いページ（FIG?）」をゼロにする**。`ci-finalize.sh` は FIG? があると止まる（今回だけ通すなら `--allow-no-figs "<理由>"`・理由が出力に残る）。HTML/CSS で組んだ図解は外枠に `class="ci-fig"` を付けると図として数える。
- CIスライドの作成依頼では、フック（`ci-slide-options-nudge.sh`）がこの既定を毎回 Claude に伝える。

### 0-1. 図を「誰が」描くか（v3.10 追補）

| 場面 | 描き手 | しくみ |
|---|---|---|
| 作成依頼の質問で **④マルチエージェント** を選んだ | Claude の複数担当（作成→レビュー） | `workflows/ci-deck-figures.js`（④の選択＝利用者の依頼として実行） |
| ④を選ばない通常の作成 | Claude が1人で描く | 本書2〜5章。表・箇条書きのページは `ci_figs.py autofig` で補える |
| 週次・月次ビルダー（ci-weekly-deck） | 自動 | ビルダーが生成の最後に `ci_figs.autofig` を呼ぶ |

- **`ci_figs.py autofig <deck.html> [-o out]`**：図の無い本文ページに、そのページの内容から図を自動で作る。
  - 表に数値の列がある → 横棒（合計行は除く・最大の行を濃く）
  - 同じ数の箇条書きが2つ並ぶ → 左右の対応図（例：課題 → 方向性）
  - 番号付き・「打ち手」「ステップ」等の順番がある箇条書き → 矢印でつないだ流れ
  - その他の箇条書き（3〜6項目）→ 一覧カード（矢印を付けない＝ありもしない順序を示さない）
  - 表も箇条書きも無いページはそのまま（FIG? に残る＝人か Claude が描く）。何度実行しても二重に入らない
- 自動の図は「最低限の保証」。経営向け・重要な資料は ④ で仕上げる。社員向けの標準手順は Claude だけで完結させる（外部LLMは使わない）。

## 1. 仕組み：図は「1ページ1ファイル」の断片として置く

```
deck.html          … 完成したデッキ（ビルダーの出力でも手書きでもよい）
figs/p3.html       … ページ p3（section の id）に足す図。id が無いページは 2桁のページ番号（03.html）
figs/p5.html
```

- `python3 5co-CI-kit/ci_figs.py inject deck.html figs/ -o deck.figs.html`
  → 各断片を**そのページの本文末尾（出典の note-line の直前）**に差し込む。元のデッキは上書きしない。
  差し込んだ箇所は `<!--ci-figs:p3-->…<!--/ci-figs:p3-->` で囲まれる（後から探せる）。
- ビルダー（Python で組むデッキ）の場合は、ビルド後に `inject` を呼ぶか、ビルダー内で `ci_figs.inject(html, ci_figs.load_figs(dir))` を使う。
- **なぜ断片にするか**：図の担当を複数人・複数エージェントに分けても同じファイルを触らない（衝突しない）。
  差し替え・取り外しがファイル1つで済み、本文の検品結果を壊さない。

## 2. 描き方（CI 準拠・厳守）

| 項目 | 規定 |
|---|---|
| 色 | CSS 変数だけ：`var(--ink)` `var(--crystal)` `var(--crystal-55)` `var(--crystal-25)` `var(--white)`、濃淡は `var(--ink-85/60/14)`。グレー直指定・#000・他の色相・琥珀は使わない（琥珀は要点ラベルと洞察セル専用） |
| 書体 | 書かない（ページ側の明朝が当たる）。数字を欧文にするときだけ `font-family:var(--serif-en)` |
| 文字 | 描画後の実寸で 10px 以上。SVG は viewBox 幅 ≒ 表示幅（約 640〜940px）にして `font-size` 10 以上 |
| 線画 | ピクトグラム調。線幅は 1.5 前後で統一、角は丸く。装飾過多にしない（静謐・上質・余白多め） |
| 形式 | インライン SVG か HTML/CSS。外部画像・外部フォント・JavaScript は使わない |
| 画像の例外 | 書籍の表紙・原本スライドの**写真**、および商品を特定するための**商品写真**は `data:` で埋めてよい（3色ルールの例外。出典を明記）。外部 URL の画像は使わない |

## 2-1. 画像アセット（ロゴ／商品画像／カテゴリー）（v3.11 強化・2026-10-28）

**写真を多用する。** 社内デッキなどで特定の企業・組織・商品・カテゴリーを示すページでは、次を守る（SKU・ブランドの取り違えを防ぐため）。

| 項目 | 規定 |
|---|---|
| 写真 | 可能な限り実写・生成写真を使う（文章と表だけにしない） |
| 企業名・組織名・商品名 | **必ずロゴ**を置く（ロックアップ／公式ロゴ。歪めない） |
| 商品名・ASIN／商品コード | **必ず代表商品の商品画像**を置く（SKU 識別） |
| カテゴリー | 相応しい画像を**生成または WEB から取得**して載せる |
| 形式 | `data:image/...` の埋め込みのみ。**外部画像 URL は禁止**（`ci_figs.py lint` の外部参照禁止と同趣旨） |
| 例外の位置づけ | 「画像の貼り付けより CI で描き直す」（§4）の例外。枠組み図・フロー図は従来どおり CI で描き直す。**実物 SKU を識別するための商品写真／公式ロゴは貼ってよい**（書籍の表紙と同じ写真例外） |
| 3色 | 描画する図は3色ルールを守る。商品写真・ロゴ写真は写真例外（色相を問わない） |
| データ表記 | スライド上に **「Ignite」と書かない**。データ出典の文言は **Shelpha**（例：Shelpha 推計） |
| 置けないとき | その `section`（または該当スライド）に `data-product-img-exempt="理由"` を付ける（`data-fig-exempt` と同型）。黙って省かない |
| 置き方 | 装飾の全面写真にしない。名称・ASIN の近く（カード／行）に小さく置く |

- 検品：`product_image_check.py`（**ASIN** 様トークンに加え、**商品名**の CamelCase／PascalCase トークン〔例 NailEnvy〕があるのに代表商品画像が無いページを `PRODUCT_IMG?` で警告。ロゴ・`dg-photo`／`figs/digest` は商品画像に数えない）。`ci-gates.sh` に警告として接続（ゲートは落とさない＝warn-only）
- 出典は写真の近くか note-line に明記する


## 2-2. 人物写真（ダイジェスト Amazon人物型）（v3.12・2026-10-29／2026-10-30 追補）

- 置き方は `DIGEST_GUIDE.md`「Amazon人物型」。人物は架空・無加工（色・ベタ・半透明・ブレンドを重ねない）・alt に「架空の人物・イメージ」。
- 人物素材の合否は下の「**人物素材の標準（2026-10-29／30）**」の9項目で判定する（旧「v2 待ち」を置き換え）。v1 素材（肌がイラスト調）は kit に入れない。kit は**規定と検品ツールだけ**を持ち、人物素材そのものは同梱しない。承認済みで本番に使えるのは marketer の3枚（`facing_marketer_01_v5_fix.png`〔下端をスライド下端か机・カウンターに接して置く〕・`facing_marketer_02_v4.png`・`facing_marketer_03_v5.png`・v3.12.5）だけ。**例外（v3.12.4・2026-10-30）**: 下の検品をすべて通った正面向きの人物素材 v3 の5枚だけを `digest_person/photo/cutouts/facing_*_v3.png` に置く（**審査待ち・未承認**＝2段審査でフォトディレクター不合格のため推奨セットとして使わない・2026-10-30）（PR #1220 の v2 6枚の置き換え。v2 と透過化スクリプトは入れない・一覧と検品結果は同フォルダの `README.md`）。
- 人物の画像は商品画像に数えない（`product_image_check.py` の `dg-photo`／`figs/digest` 除外と同じ扱い）。
- **切り抜きの白フチ検品（2026-10-30・強化版）**: 白い背景を色で抜いた切り抜きは、髪の毛先などの半透明部分や頬・耳の横に元の白が残る（白地のページでは見えない）。`cutout_halo_check.py` は3種類を見て、どれか1つでも塊があれば `HALO?` を出す。①**edge**＝輪郭3px以内で暗い髪に隣接した白っぽい画素の塊（40px以上） ②**blob**＝背景の白に近い不透明な塊で、透明部に接し周りの過半が髪・肌のもの（**帯より太い白い塊も大きさ不問で拾う**。旧デフリンジで灰色に塗られた平坦な塊も。白ブラウス・クリームのニットなど服サイズの明色は対象外） ③**ink**＝濃紺 #101820 に合成して輪郭が内側より明るく光るもの（**暗い背景で光るフチ**・半透明の白い縁・色の脱汚染をしていない毛先）。`--resize 1152,813,406,284,142` を付けると、サイト側と同じ普通の縮小（非プリマルチプライ）をかけた各幅でも再検査する（透明画素の RGB が白のままだと**縮小した時だけ白線が出る**。元幅以上の幅は無視）。`ci-gates.sh` はデッキ内の透過 PNG を自動で検査し（デッキ内は縮小判定なし・グラフ線などの幅1pxの塊と ink は数えない＝白地で抜いたロゴの縁の誤検知防止）、素材フォルダは `--cutouts <alpha_dir>` で縮小判定込みで検査する（既定は警告・`--strict` で落とす。縮小幅は環境変数 `CI_HALO_RESIZE`／デッキにも掛けるなら `CI_HALO_DECK_RESIZE`）。確認は `--out <dir>` の確認画像（濃紺背景に重ね、edge=赤／blob=マゼンタ／ink=橙）で行う。`HALO?` が出た素材は古い切り抜きを直さず、元写真から下の手順で作り直す。判定の正本は CIスライドの検品メモ（HALO_CHECK_HARDENING・2026-10-30）
- **人物素材の生成と受け渡し（2026-10-30・若松さん決定）**: いまの画像生成ツールは透明な背景を出せない（「透明に」と指定すると市松模様が絵として描かれる）。そのため ①背景は載せる先に近い無地の中間グレーかクリスタルブルー寄りの青で生成する（白地・濃いグリーンは使わない。毛先に残った色が目立つため） ②専用の切り抜きモデルで切り抜き、どの素材にも切り抜き版（`alpha/` の PNG）を必ず添える（サイトのダイジェスト帯は乗算合成のため、色つき背景の元画像だけでは人物の周りが四角く濁る） ③`cutout_halo_check.py --resize 1152,813,725,406,362,284,142 --bg-residue` を通してから渡す。縮小して使う場合は縮小後の画像でも検品する
- **背景色の取り残し検品（2026-10-30）**: 白フチの3種類（edge／blob／ink）は「白っぽい」フチしか見ない。元写真の背景が灰色・茶系などの中間調だと、隙間や肩・髪の端に背景が残っても OK になる。`--bg-residue` を付けると④**bgres**＝元写真（`--src`、未指定なら `<alpha の親>/../src/` の同名系）に自動で位置合わせし、背景の色に近く前景の色では説明できない中間調の塊（輪郭から 10px 以内または閉じた穴の中・30px 以上）を `bgres` として NG にする（確認画像はシアン）。元写真が見つからないときは `bgres SKIP`（`--bgr-require-src` で NG）。本体＝`cutout_bg_residue.py`。既定値＝`--bgr-dist 10 --bgr-tol 12 --bgr-margin 20 --bgr-min 30 --bgr-ymax 175`。**付けなければ従来と同じ出力**（`ci-gates.sh` 互換）。位置合わせに 1 枚 5〜20 秒かかる（`--src key=FILE` で候補を絞ると速い）
  - **運用（2026-10-30）**: **人物素材（`facing_*`）は納品前に必須**＝`python3 5co-CI-kit/cutout_halo_check.py <alpha.png> --resize 1152,813,725,406,362,284,142 --bg-residue` が OK、**加えて目視**。**シーン素材（`ec_*` など）は警告扱い＋目視判定**（暗いジャケットの縁の毛羽・スマホのカメラの縁・ノートPCのキーボード・白髪交じりの毛先が背景色に近いと偽陽性寄りに NG が出る）。`ci-gates.sh --cutouts <alpha_dir>` は当面 bgres を**警告のみ**で回す（`--strict` でも落とさない。`CI_HALO_BGRES=0` で省略）
  - **既知の弱点**: 背景と服・肌がほぼ同じ色のとき（例：茶灰の背景×同系色のセーターの毛先と肩の間の筋）は色だけでは区別できない＝**検品 OK でも残る**。目視を省略しない
  - **手に持つ小物（ボトル・スマホ等）や腕の内側の隙間を「不透明で埋める」処理をしない**（2026-10-30 consumer_03 の不具合の原因＝旧 `make_alpha_facing_v2.py`。kit には入れない）。隙間は透明のまま、専用の切り抜きモデル＋`cutout_matte.py` 相当の処理で作る

- **切り抜きの作り方（標準・2026-10-30・若松さん承認）**: ①元写真から作る（古い alpha を直さない）。専用の切り抜きモデルのマスクを使い、髪の帯だけ透明度を推定（matting）し、前景色を推定して背景色を脱汚染する。不透明部は元画素のまま（色かぶせ・下端フェードをしない） ②**alpha bleed（必須）**＝保存前に透明画素（alpha=0）の RGB を最寄りの不透明画素の色で埋める（サイト側の縮小で白線が出ない） ③`cutout_halo_check.py <png> --resize 1152,813,725,406,362,284,142 --bg-residue` が OK（スマホを持つ素材は `phone_speck_check.py` も OK） ④濃紺 #101820 とクリスタルブルー #C3D7EE に合成した全体図と髪・手・スマホの縁の拡大を実際に見て、白フチ・もや・欠け・**背景と同じ色の服・肌の縁に残った背景**がないことを確かめる ⑤渡すのは `alpha/` の PNG（alpha bleed 済み）。既知の弱点＝ノートPC・スマホの銀色の縁（実物のハイライト）が暗い本体の隣にあると blob/ink が反応することがある（人物には影響なし。確認画像で目視して判断）

- **人物素材の標準（2026-10-29／30・若松さん決定）**
  1. **ロゴ・ブランドの印を写さない**：服だけでなく**スマホ・PC・タブレット・イヤホンの背面・画面も**。生成で出たら消す（例：タクシーのコンサル v8＝`ec_m03_taxi_consultant_v8_nologo`）。白い完全ワイヤレスイヤホンは使わない。
  2. **機器・小物の大きさは人物に対して実物どおり**（スマホが手より大きい・PC が小さすぎる等は不合格）。
  3. **画面の向き・手指・影**：画面は持つ人の側か閉じた状態。指の本数・関節・持ち方が自然。光と影の向きが顔・服・小物で一致。
  4. **顔の写真らしさ**：顔を等倍で切り出し、以前の写真（`ec_m02_funnel.jpg` 等）と同等以上であること。
  5. **生成時の背景**：無地の中間グレー（#9AA3AD 前後）か #C3D7EE 寄りの青（白・濃いグリーンは不可）。どの素材にも `alpha/` の PNG（alpha bleed 済み）を添える（2026-10-30 決定。「場面で生成してから切り抜く」とする旧案より優先）。
  6. **重ねない・消さない**：人物の**手前**に crystal blue（#C3D7EE 系）を半透明で重ねない（色面・プレートは人物の後ろだけ）。人物写真の**下端をグラデーションでフェードさせない**（2026-10-30 禁止。下端は色面の底で切る＝`DIGEST_GUIDE.md` の `clip-path` の下辺）。
  7. **服（オフィス・会議シーン）**：欧州のハイブランドのオフィス服の空気（同系色で重ねる・上質な生地・ロゴなし・アクセサリー1点まで）。**黒スーツ×白ブラウス／白シャツは不可**（就活・制服感を出さない）。自宅シーンは普段着のまま。詳細＝社内スタイルガイド（office-wear-styleguide・CIスライド側で管理。kit には要約のみ）。
  8. **審査**：**衣装ディレクターとフォトディレクターの2段審査を両方通った素材だけを若松さんに見せる**（片方だけの合格・審査前の素材は見せない・2026-10-30）。衣装ディレクター＝服・ヘアメイク、フォトディレクター＝光・構図・動き・肌（下の「生成ルール」）。検品記録を残す。
  9. **検品**：`cutout_halo_check.py --resize 1152,813,725,406,362,284,142 --bg-residue` が OK／スマホを持つ素材は `phone_speck_check.py`（スマホ周りの浮いた点・細線）が OK／#101820・#C3D7EE に合成した全体と髪・手・スマホの縁の拡大を**目視**。

- **人物素材の生成ルール（2026-10-30・若松さん確認・フォトディレクター／衣装ディレクター）**：上の標準1〜9に加えて守る。出典は CIスライド側のナレッジ（`/workspace/knowledge/design/…`・kit には要約のみ）。
  1. **プロンプトは「撮影の状況」を書く**：「実際のカメラで撮った、会社サイト用の自然なプロフィール写真」のように、どこで・どう撮ったかを語る。肌の毛穴・シミを細かく指示しない（誇張されて描き込んだ肌になる）。`8k`・`hyperrealistic`・`masterpiece`・`HDR` など品質を盛る語や、`flawless`・`beauty`・`glamour`・`studio lighting` など**美化の語を入れない**（`photorealistic` も避け `real photograph／candid／taken on a real camera` に置き換える）。「レタッチなし・美化なし」を明示する。出典＝`photo_realism/2026-10-30_natural-person-photo-techniques.md` §1・§2・§5
  2. **編集はマスター（最初の良い版）から1回**：出力をさらに編集する**チェーン編集（v3→v6→v8）をしない**（編集のたびに描き直され、髪が描線・肌が油絵のようになる）。変更点は1回にまとめ、崩れたらマスターに戻って作り直す。衣装だけ変えるときは「X だけ変える・顔・表情・光・画質は変えない」と毎回書く。出典＝同 §1 #1・#7・§4、`photo_director/2026-10-30_baseline-shooting-spec.md`「生成」
  3. **光は窓からの自然光だけ・明暗比 1:3**：片側の窓の外光を約45°で当てる。ストロボ・定常光・天井照明・レフ板の起こし・リムライト・正面からの均一な光は使わない。切り抜き用に無地背景で撮るときも、窓辺に無地の中間グレーを立てて同じ向きの自然光で撮る（スタジオの白バック・グレーバックは不可）。出典＝`photo_director/2026-10-30_baseline-shooting-spec.md`「共通ルール」・C
  4. **動きは自然に・さりげなく**：動きを入れるのは移動中（歩行・廊下・階段・タクシー）と会議の場面だけ。静止ポートレートには入れない。「間の瞬間」（呼ばれて振り返る・資料に手を伸ばす・話しながらの手・立ち上がる）を選び、ジャンプ・疾走・風になびく髪などの大げさな動き、左右対称の手足、全員が同じ向き・同じ歩幅で動く構図は使わない。顔は止め、ぶれは手や紙の端だけ・動作の向きに合わせる。出典＝`photo_director/2026-10-30_portrait-movement-research.md` 冒頭・§3・§4
  5. **コンサルタント役は格上げした装い（ラグジュアリー層）**：目の詰まったウール・カシミヤなど質感の写る生地、肩の合った仕立て、本切羽の袖ボタン、薄いソールのローファー、薄い文字盤の革ベルト時計（小物はそれだけ）、毛先まで整った精密なヘアカット。安っぽい平板な生地・厚いゴム底・固めた髪・つるつるに加工した肌は不可。生活者役は対象外。出典＝`costume_director/2026-10-30_consultant-luxury-tier.md`
  6. **肌**：美化の語を入れない・**顔の修復（GFPGAN／CodeFormer／「顔を補正」機能）をかけない**・**AI アップスケーラーを顔にかけない**（どうしても拡大するなら2倍まで・顔補正は切る）・美肌フィルターやスムージングをかけない。**CI に使う顔は顔幅 180px 以上**（判定の下限は 130px）。グレインは輝度のみ σ2〜3・切り抜きと合成の後に1回だけ（グレインで不合格の肌は直らない）。出典＝`photo_director/skin/2026-10-30_skin-realism-knowledge.md` b4・c1・c2、`photo_director/skin/2026-10-30_skin-checklist.md`
  7. **レビューに肌の測定結果を添える**：生成直後のマスター（グレイン前・PNG）で `python3 skin_metrics.py <画像> --json --debug dbg.png`（本体＝`/workspace/knowledge/design/photo_director/skin/skin_metrics.py`・kit には入れない）を実行し、出力（JSON）と dbg.png をフォトディレクターのレビューに添付する。数値は見落とし防止の補助で、合否は100%表示の目視で決める（目視で1つでも不合格のしるしがあれば不合格）。チェックリスト＝`photo_director/skin/2026-10-30_skin-checklist.md`

## 2-3. 差し色イラスト（2層・v3.13・2026-10-31）

出典＝うちた（note）「パワポに貼ると、資料の色に変わるイラストの作り方」（2026-10-08）を CIスライドが提案。記事のテラコッタ差し色・くすみ8色パレットは採らない。

- **イラスト（人物写真ではない絵）は「グレーの土台」と「差し色の層」の2層で作る。差し色は1枚につき1か所だけ**。
- HTML では差し色の層を `mask-image` にして `background: var(--crystal)` で塗る＝**色は CI トークンに自動で追従**（`ci-illus-v3.13.css`・`ci_figs.py lint` の3色ルールを満たす）。土台は ink 系のグレーのみ（CSS でも `filter:grayscale(1)` を掛ける）。差し色の色を断片に書かない。
- 断片は手書きしない：`python3 5co-CI-kit/ci_figs.py illus base.png accent.png --alt "場面の説明" [--width 360] -o figs/p05.html`。base＝グレーの土台（PNG・背景透過）、accent＝差し色を置く1か所の形（土台と同じ縦横比の透過 PNG・アルファだけを使う）。土台に色がある（1%超）・形が空／全面・縦横比が違う・ファイル名が人物素材（`facing_*`）のときは作らない。
- 検品＝`ci_figs.py lint`（`figure.ci-illus` ごとに差し色の層がちょうど1つ・土台 `img.ci-illus-base` がある・差し色の色を書いていない・土台がグレー〔Pillow がある環境〕・人物写真を使っていない）。`ci-gates.sh --figs figs/` で毎回走る。
- 生成プロンプトの成功基準：**背景透過・文字/数字/ロゴなし・場面の理屈が通る（画面は使う人の方を向く）・端で切らない・下端を水平に切らない**（当社の人物素材の基準と一致）。
- **人物の写真素材は対象外**（フォトディレクターの担当＝2-2）。人物写真に差し色を重ねない。

## 3. 置き方と中身

1. **ページに書かれていない事実・数字・主張を足さない**。ラベルは本文の言葉を使う。素案の数字は「案」「試算」と書く
2. **1ページ1図**（小さなピクトグラムの組は1つの図として数える）。すでに図がある高密度ページは「追加不要」と判断してよい
3. **本文の下の空き領域に in-flow で置く**（absolute で重ねない）。幅は本文幅の範囲、フッターから 8mm 以上離す
4. 必要なら短い「図の読み方:」を `t-note` で添える
5. **ページからはみ出したら図を小さくする。本文は削らない**
6. **図の中の動き（動く資料）は、見出しの判断を確かめるものだけ**。飾りの動きは入れない。量の動き（棒の長さ・並び順）は値から計算する（2026-10-30・`V3.2_FORMAT.md`「動く資料」の1枚1操作）

## 4. 原本の図を CI で作り直すとき

- **画像の貼り付けより、CI で描き直すことを基本にする**。原本のカラー・書籍画像はそのまま載せない
- **構成と言葉は原本に忠実に**（列・段・矢印・ラベルを変えない）。色だけを3色に置き換える
- **個人名は役割名に置き換える**（社員＝アカウント・プロデューサー等、顧客企業の担当者＝職位のみ）。退職者の名前を現役として残さない
- 原本に無い情報（例：Grade の対応案）は図に足さず、根拠パネルか注記に「案」として置く
- 原本の誤字（例：WISDAM）は正式表記にそろえ、根拠パネルに書き残す

bash 5co-CI-kit/ci-gates.sh /tmp/deck.figs.html --figs figs/               # あふれ・重なり・SVGラベル＋figs lint

- 断片のレビューでは「本文と言葉が合っているか」「新しい事実を足していないか」も見る

## 6. マルチエージェントで進める（workflows/）

利用者が「マルチエージェントで」「コンペで」と頼んだときに使う（Workflow ツールの利用者オプトインが前提）。

| 型 | ファイル | 流れ | 実績 |
|---|---|---|---|
| 並列制作＋レビュー | `workflows/ci-deck-figures.js` | ページを 3〜5 グループに分け、グループごとに「作成 → レビュー・修正」の2段を pipeline で流す | 17ページ／10エージェント／約7分 |
| デザインコンペ | `workflows/ci-figure-competition.js` | 1枚の図を 4 つの方向性で並列制作 → 観点の違う審査員3人が 4観点×10点で採点 → 優勝案に他案の良い点を取り込んで仕上げ | 4案＋審査3＋仕上げ1＝8エージェント |

- 呼び出し：`Workflow({scriptPath: "5co-CI-kit/workflows/ci-deck-figures.js", args: {...}})`（引数は各ファイル冒頭のコメント）
- **グループ分けの目安**：物語の区切り（導入／定義／本編／参考／運用）で切る。1グループ 3〜4 ページ
- **コンペの方向性の例**：原本に忠実な洗練版／循環を主役にしたリング型／線画中心のエディトリアル／パネル型インフォグラフィック
- **審査の観点の例**：経営陣（一目で伝わるか・品位）／CI デザイン監修（3色・余白・整列）／原本作成者（意味が正確か）
- 全案の断片と PNG は残す（会議で「別案の方がよい」と言われたときに差し替えられる）

## 7. やらないこと

- 図のために本文・見出し・表を書き換えない（図の都合で本文を削らない）
- 1枚のページに図を重ねて足さない（2つ目が要るならページを分ける）
- 琥珀・写真以外の色付き画像を「雰囲気づけ」に使わない
